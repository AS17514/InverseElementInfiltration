# 配置资产协作公约（2026-08-09）

> 背景：模板库合并时，双方独立生成同一批 Tpl 资产（GUID 随机分配，两边不同）→ 43 个冲突。
> 目的：避免"派生物（.asset + .meta）被多人独立生成提交"导致的 GUID 分叉。
> 适用范围：Assets/Settings/ 下全部配置资产（棋子/能力/关卡/地图/事件/遗物/模板）。

---

## 核心思想

```
JSON = 人写格式（权威源——可 diff、可审、无 GUID）
资产 = 派生物（机器生成——GUID 随机、不可手动 diff）
→ 派生物【单一角色生成提交】；其他人只 pull 消费
```

## 公约 6 条

```
1.【单一生成者】Assets/Settings/ 下 .asset 一律由【后端】统一生成并提交；
   UI 侧只 pull 使用，不自行跑导入器生成资产。
   本地测试生成可以，但【不得提交】生成物；若必须提交——先 pull 并确认仓库无同名资产。

2.【提交前检查】git status 出现 Assets/Settings/**/*.asset 或 .meta 的
   未跟踪/修改时，先查 git ls-files 是否已有同名——有则用仓库版本，不覆盖。

3.【生成前先 pull】任何导入器/收集工具运行前先 pull 最新
   （基于最新生成，减少分叉）。

4.【冲突标准】资产/meta 同名冲突 → 取"被场景/预制体引用"的那边；
   两边均未被引用 → 取任一边（同一 JSON 生成，内容等价）。
   （2026-08-09 实例：Tpl 资产冲突取 ours——因为 Bootstrap.prefab 引用我们的 GUID）

5.【JSON 是权威源】一切配置修改改 JSON + 跑导入器；资产不手动改。
   导入器保持增量模式（不删旧建新——GUID 不变，场景引用不断）。

6.【工具归属】导入器/收集工具由后端维护；新增功能先对齐再实现。
```

## 检查清单（提交前）

```
[ ] git status 无 Assets/Settings/** 未跟踪 .asset/.meta（或已确认是新增且仓库无同名）
[ ] 导入器运行前已 pull 最新
[ ] 资产修改均来自"改 JSON + 跑导入器"（无手动编辑资产）
[ ] 提交信息注明资产来源（如"导入生成"）
```

## 常见冲突处理

| 情况 | 处理 |
|---|---|
| both added 同名资产/meta | 取被引用方；都没被引用取任一边 |
| both modified 资产 | 说明双方都改过资产——以 JSON 重新生成为准（跑导入器覆盖） |
| both modified 场景（Main.unity） | 手动合并（保留双方 override——引用仓库已提交资产的 GUID） |

## 美术 / 音频 Git LFS 公约（2026-08-21 决议）

> 目的：前端会持续提交 UI / 美术图片，协作者会提交音效与 BGM 等二进制资源。为避免普通 Git 历史随资源迭代持续膨胀，项目从本公约提交起启用 Git LFS 管理新增二进制资源。

### 适用规则

1. `.gitattributes` 已配置下列资源由 LFS 跟踪：
   - 图片 / 美术源文件：`png`、`jpg`、`jpeg`、`webp`、`gif`、`psd`、`tga`
   - 模型源文件：`fbx`、`blend`
   - 音频：`mp3`、`wav`、`ogg`、`aif`、`aiff`、`flac`
   - 其他大二进制：`ttf`、`pdf`、`zip`、`unitypackage`
2. **绝不将** `.meta`、`.prefab`、`.unity`、`.asset`、JSON、代码及其他文本文件纳入 LFS。
   - `.meta` 保存 Unity GUID，必须与资源本体同时提交，但保持普通 Git 文本文件，便于引用与冲突处理。
3. **不迁移既有历史资源**：本规则只接管新增资源或后续重新提交的匹配资源；`.gitattributes` 会显式排除当前已在普通 Git 历史中的二进制文件，避免检出时被 LFS 误判为 pointer；不得自行执行 `git lfs migrate` 重写仓库历史。

### 协作者操作与提交检查

```bash
# 每台开发机首次执行一次
git lfs install

# 确认当前仓库实际被 LFS 跟踪的文件
git lfs ls-files

# 提交前确认某个新资源会命中 LFS 规则
git check-attr filter -- Assets/Art/示例.png
```

提交美术 / 音频时：

```
[ ] 资源本体与同名 .meta 一并提交（资源进 LFS，.meta 留在普通 Git）
[ ] git check-attr 确认资源 filter=lfs
[ ] git lfs ls-files 能看到已暂存 / 提交的资源
[ ] 不提交 Library/、导入缓存或临时导出物
[ ] 不改写既有普通 Git 资源历史
```

### 远端与外部下载

1. 所有协作者必须安装 Git LFS，并确认可访问远端 LFS 服务后再提交大资源。
2. GitHub LFS 存储与流量配额需要持续关注；资源规模增长后由团队共同决定是否升级配额。
3. 若仍需让外部同学用 GitHub ZIP/TAR 获取完整项目，仓库管理员必须开启“在源码归档中包含 Git LFS 对象”，并在首次启用后下载归档实测图片和音频是否为真实文件；否则统一使用 `git clone` 获取项目。
4. LFS 规则调整、历史迁移或大批资源导入属于跨端协作事项，必须先对齐后执行。
